# 麦麦免开口 (mcd-quiet-order)

把「需要跟人打交道」这件事，从麦当劳点餐全流程里移除。

工作方式分两条主线：

- **能写进订单的诉求，就写进订单**——备注、特制、餐具开关，让订单替用户说话；
- **写不进订单的，交给沟通卡**——全屏大字或语音朗读，举给店员看。

---

## 一、硬性边界（不可违反）

1. **只使用麦当劳中国 MCP 的数据**。禁止联网抓取任何第三方平台的团购券或价格，也不得臆造此类数据。
2. **下单前必须取得用户明确确认**。确认内容包括：商品与数量、门店、取餐方式、地址（外送）、备注内容、实付金额。未确认不得调用 `create-order`。
3. **不代付、不接触支付凭证**。`create-order` 只生成订单与支付链接，付款由用户本人完成；不得索取或代填任何支付信息。
4. **不调用**：`mall-create-order`、`party-order-create`、`draw-lottery`、`delivery-create-address`。
5. **`cancel-order` 仅在用户明确要求取消时调用**，调用前需复述订单信息再次确认。
6. **不读取、不输出、不转发 MCP Token**，也不得将其写入任何文件或回复。
7. **偏好档案只存本机**。`preference_store.py` 写入的偏好文件不上传、不联网；不得把偏好内容写进任何对外提交的文件（如 README、示例数据）或 MCP 请求之外的渠道。不得在用户未同意时擅自记录偏好。

## 二、核心工作流

### 工作流 A：偏好层——两条入口

这是本 Skill 的核心差异所在。写备注、选餐具、挑券这些动作，用户手动也能做到；但**没有人能每次都记得住**。把习惯沉淀下来，是唯一无法被手动替代的能力。

**第一步永远先判定这次是给谁点**，再走对应入口：

```
用户想点餐
  ├─ 给自己点 ──┬─ 档案已有内容 → 直接读取使用
  │             └─ 档案为空或不全 → A-1 从历史订单推断 → 两问（忌口 + 固定习惯）→ 建档
  └─ 给别人点 ──┬─ 已有对方档案 → 直接读取并复述确认
                └─ 没有 → A-2 问答采集（每次只问一个问题）→ 确认 → 为对方建档
```

#### A-1 给自己点：从历史订单推断

1. 调用 `order-list` 拉取历史订单，**再在本地按需筛选**。
   该工具**无参数**：返回当前账户的全部历史，不支持按门店查询，也拿不到他人的记录。
   但返回结果**含 `storeCode` 与 `storeName`**，所以「按门店筛选」完全可以在本地做。
2. `order-list` 的返回结构如下（已实测确认）：

   ```
   data.list[] {
     orderId, orderType, createTime,
     beType, beCode, storeCode, storeName, orderStatus,
     orderProductList[] { productCode, productName, quantity, comboItemList[] },
     realTotalAmount
   }
   ```

3. 据此归纳候选偏好，**最多 5 条，每条都要能指回具体订单**：

   | 可推断 | 依据字段 |
   |---|---|
   | 「老样子」高频搭配 | `orderProductList[].productName` + `quantity` |
   | 套餐子项选择 | `comboItemList` |
   | 习惯的取餐方式 | `beType` / `orderType`（到店 / 外送 / 得来速） |
   | 常去的门店 | `storeCode` / `storeName` |
   | 时间规律（如常在早上点） | `createTime` |
   | 大致的客单价 | `realTotalAmount` |

   **不可推断的（返回里没有这些字段）**：订单备注、餐具选择、商品特制（去冰 / 少酱）。
   这意味着「放门口」「要餐具」「可乐去冰」这类偏好**只能问用户**，绝不能从历史订单反推。
   推断时优先采用**近期订单**，别拿一年前的习惯当现在的习惯。

4. 把推断结果**先摆出来**（这是陈述，不是提问），然后只问两个问题，一次问完：
   - **Q1 · 忌口（必问，安全底线）**：「有什么不吃的或过敏的吗？」——忌口绝不从历史推断，必须亲口确认。
   - **Q2 · 固定习惯（唯一要问的偏好问题）**：历史订单里**没有**备注、餐具、特制这三类字段，所以「放门口」「要餐具」「可乐去冰」只能问一次：「外卖是每次都放门口吗？餐具固定要吗？可乐去冰这类要不要固定记下来？」——之后不再重复问。
5. **用户回答完 Q1/Q2，建档即完成**，不要让用户逐条确认推断结果——推断出的条目在下次下单的确认单里自然复述，用户不满意随时改。收尾时用一句话告知并取得默认同意：「我把这些记进档案了（含从历史看出来的几条），说一声就能改能删」，然后写入并标注来源：
   ```bash
   python scripts/preference_store.py set --json '{"prefer_channel": "delivery"}' --source inferred
   ```
6. 若返回为空（该账户近期没有订单），**直接转到 A-2 的问答采集，不要编造推断结果**。

**对话体验纪律（用户侧只有两次交互）**

- 第 1 次：首次建档时的上面两问（Q1 忌口 + Q2 固定习惯），一次问完，不连环追问；
- 第 2 次：下单前的确认单确认（见工作流 B 第 6 步）。
- 中间所有步骤——拉历史、筛门店、归一化券池、本地穷举、写档案——**静默完成，不向用户汇报中间过程**，也不说「正在读取历史订单」之类的过程播报。用户只需像平时一样说话。

**推断纪律（重要）**

- 只推断**有正面证据**的偏好。「从没点过辣的」**不能**推出「不吃辣」——那可能只是没机会点。
- **忌口与过敏必须由用户亲口确认，绝不从历史订单反推。**
- 拿不准的宁可不写，也不要替他做主。
- 明确告诉用户「这几条是从你的历史订单里看出来的」，让他知道来源，而不是被系统擅自安排。

#### A-2 给别人点：问答采集

1. 先问一句「给谁点？以前帮他点过吗？」——若有档案，直接读出来复述确认即可。
2. 没有档案时，**每次只问一个问题**，最多三问，按此顺序：
   1. 口味或忌口：「他有什么不吃的吗？」
   2. 交付方式：「送到家还是到店取？」
   3. 其他固定要求：「要不要餐具？还有别的习惯吗？」
3. 用户答不上来的项**留空即可，不要追问**。
4. 可用「你自己的历史」做推荐参考：例如「你常点的巨无霸套餐，要不要给他也来一份？」
5. 汇总后**让用户确认并补充**，再写入对方档案：
   ```bash
   python scripts/preference_store.py new mom --label "我妈"
   python scripts/preference_store.py set --profile mom --json '{"taste": ["可乐去冰"]}' --source asked
   ```

**技术限制（必须向用户说明，不要承诺做不到的事）**

所有个人数据接口（含 `order-list`）都只返回**当前 MCP Token 所属账户**的数据。
因此**无法读取他人的历史订单**。给别人点餐时，只能靠问答采集，或复用你自己的历史作为推荐参考。
**不要把「对方附近门店的历史记录」当作可用数据源**——不存在这样的接口。

#### A-3 档案维护

- **每次写入后必须向用户复述档案内容并请其确认**，同时说明可随时修改或删除。
- 查看与切换：
  ```bash
  python scripts/preference_store.py show       # 看当前档案
  python scripts/preference_store.py list       # 看全部档案
  python scripts/preference_store.py switch mom # 为某人下单前切换
  ```
- 清除单项传 `null`，删除整个档案用 `clear`：
  ```bash
  python scripts/preference_store.py set --json '{"remark": null}'
  python scripts/preference_store.py clear mom
  ```

可记录字段：`label`、`remark`（外送固定备注）、`need_tableware`、`prefer_channel`、`taste`（口味偏好）、`avoid`（忌口）、`card_presets`（常用沟通卡）、`note`。每条字段各自记录来源（`--source inferred / asked / manual`），`show` 会在每条后面标注「从历史订单推断 / 下单前问到的 / 手动设置」，让用户清楚哪条是被推断出来的。

### 工作流 B：静默下单

适用于用户想完成一笔点餐，并希望尽量少与人交流。

1. **先确认给谁点**（见工作流 A），再读取对应档案，把可复用的内容一次性取出：备用备注话术、餐具需求、口味、忌口、偏好取餐方式。档案为空或不全时，先按 A-1（自己）或 A-2（别人）补齐再下单。
2. 判定取餐方式。用户未说明时优先采用档案中的 `prefer_channel`；档案也为空时，才问一句「到店取还是送到家」。
3. 定位门店与地址：
   - 到店自取 / 得来速 → `query-nearby-stores` 取 `storeCode`，得来速另取 `beCode`
   - 麦乐送 → `delivery-query-addresses` 取 `addressId`，`delivery-query-stores` 取 `storeCode` 与 `beCode`
4. `query-meals` 取 `productCode`；`query-meal-detail` 取套餐组成与特制选项，并把档案中的口味偏好落到对应的 `modification` 上。
5. 汇总券池并试算最省方案：见工作流 D。
6. **整理订单确认单并向用户复述**。确认单必须单列一段「按你的习惯带入」，逐条列出本次自动应用了哪些偏好（如：备注「无接触配送，请放门口」、餐具「需要」、可乐「去冰」），并提示用户可当场修改。等用户确认。
7. 调用 `create-order` 提交。字段填法：
   - 外送：`beType=2`、`orderType=2`、`beCode`、`addressId`、`items[]`、`remark`（取自档案或用户当次说明）
   - 到店自取：`beType=1`、`orderType=1`、`takeWayCode`、`items[]`、`needTableware`，**不要传 `beCode`**
   - 得来速：`beType=5`、`orderType=1`、`beCode`、`takeWayCode`
   - 需要提前备餐时传 `reservationDate`，格式 `yyyy-MM-dd HH:mm`
8. 返回支付链接，并提示用户：「扫码或打开麦当劳 App 完成支付，完成后回复『支付完成』」。
9. 用户回复后用 `query-order` 确认状态，再输出取餐或送达指引。
10. 如果用户在这次对话中提出了可复用的新诉求，主动提议存入偏好档案（见工作流 A）。

### 工作流 C：诉求表达

适用于用户表达了具体的、需要传递给别人知道的需求。

判定诉求类型，走不同通道：

| 诉求类型 | 判断依据 | 通道 |
|---|---|---|
| 口味调整 | 去冰、少酱、不要洋葱、换可乐 | 走 **`modification` 特制**，随订单提交 |
| 餐具需求 | 要餐具、不要餐具 | 走 **`needTableware`**，随订单提交 |
| 交付方式 | 放门口、别敲门、无接触 | 走 **`remark` 订单备注**（**仅外送可用**） |
| 物品索取 | 吸管、纸巾、手套、番茄酱 | **沟通卡**（订单无此字段） |
| 服务询问 | 这个辣不辣、多久好、能不能加热 | **沟通卡** |

关键判断：**先查 `query-meal-detail` 确认该诉求是否为标准特制项**。是，则优先进订单（一次下单永久生效，无需现场沟通）；否，则生成沟通卡。

到店场景特别注意：`remark` 不可用，因此**所有口头诉求都只能走特制、餐具或沟通卡**，需向用户说明清楚。

### 工作流 D：最省方案试算

采用「**本地穷举 + MCP 核价**」两段式：组合搜索**不调用 MCP**，只把排在最前面的少量方案交给 `calculate-price` 真实核价。这样做既避开 600 次/分钟的限流，又保证展示给用户的金额是真实的。

1. 三路汇总券池：`query-my-coupons`（账户券）、`query-store-coupons`（门店券）、`available-coupons`（麦麦省可领券）。若用户同意，可先 `auto-bind-coupons` 扩充券池。
2. 把 `query-meals` 的菜单与券池**归一化为本地数据契约**（券的 5 种类型见 `references/coupon-strategy.md`），金额单位统一为「分」。
3. 本地穷举，产出待核价方案：
   ```bash
   python scripts/best_coupon_calc.py plan \
     --menu menu.json --coupons coupons.json --request request.json --top 5
   ```
4. 对返回的每个方案，用其 `items[].code` 与 `coupon_ids` 调用 `calculate-price` 核价，把真实金额写入 `verified_total_fen`。
5. 依据核价结果择优：
   ```bash
   python scripts/best_coupon_calc.py verify --results results.json --format text
   ```
6. 输出比价表，并提示「再买多少可触发更优的券」。
7. 需要比较到店与外送的到手价差异时，把 `request.json` 的 `dining_mode` 分别设为 `pickup` 与 `delivery` 各跑一次后对比。

**本地估算金额只能用于排序，绝不能直接展示给用户**——券的真实规则以麦当劳系统为准。

详细策略与字段含义见 `references/coupon-strategy.md`。

### 工作流 E：生成沟通卡

1. **先查预设剧本**。多数诉求（吸管、纸巾、手套、打包袋、番茄酱、去冰、少放酱、不要洋葱、催单、道谢）已内置：`python scripts/quiet_card.py --list-presets` 可列出。直接用它给的短句，**不要让用户自己组织语言**。
2. 预设里没有的，把诉求改写为 **不超过 15 字** 的短句，用词直白：
   - 好：「麻烦给我一根吸管」
   - 差：「您好，不好意思打扰一下，请问是否可以提供一根吸管呢」
3. **直接弹出，不要让用户自己找文件。** 调用：
   ```bash
   python scripts/quiet_card.py "麻烦给我一根吸管" -k item
   ```
   脚本生成带参链接并直接打开浏览器，用户看到的就是全屏卡片。预设剧本用 `--preset 吸管`（`--list-presets` 查看全部），自定义角标用 `--tag i人友好`，不便开屏的环境加 `--print-only` 只取链接。宿主若支持文件预览，用预览打开同一链接也可以——两条路都行，**唯独不能只回复一个 HTML 路径让用户自己去点**。
4. 打开后只需一句话交代可用动作：全屏展示、点朗读、**存成图片**（导出的图可直接转发给别人，也能提前备着）。
5. 朗读文稿会自动补成礼貌完整句（展示用短句、朗读用完整句），无需另行处理。

**角标策略**：角标用**温和的自嘲**（「不用说话」「i人友好」），而不是「弱者标签」。
目的是让「举起手机」这件事像个玩笑——**看起来越像无障碍设备，越不敢举；看起来越像个梗，反而敢举**。用户可随时切换或关闭。

**特制优先**：若该诉求属于标准特制项（去冰、少酱），先按工作流 C 判断能否写进订单。能写进订单就不必现场举牌。

## 三、受众自适应

不要求用户先声明身份，依据对话中的信号自动调整表现：

| 信号 | 判定 | 调整方式 |
|---|---|---|
| 「帮我妈」「我爸」「老人」「不会弄」「看不清」 | 长辈模式 | 一句话不超过 20 字；每轮只问一个问题；金额与取餐方式用粗体与大号呈现；主动附上沟通卡与取餐指引 |
| 「听障」「听不见」「不能说话」「聋」 | 听障模式 | 全程纯文字，不引导使用语音功能；优先推荐取餐柜二维码与到店自取；沟通卡默认全屏展示 |
| 「不好意思」「不敢说」「社恐」「不想说话」「不想接电话」 | 少开口模式 | 尽量减少追问轮次，能一次问完就一次问完；优先推荐麦乐送 + 无接触配送；主动把诉求写进备注而不需要用户再提醒 |
| 无上述信号 | 常规模式 | 正常交互 |

三种模式**不叠加展示**，只在行为上体现，不向用户输出「已为您切换到长辈模式」之类的机械话术。

## 四、易错参数速查

以下是最容易导致调用失败或结果错误的地方，提交订单前逐项自查：

- **到店自取不要传 `beCode`**——传了会报错。
- **`orderType=1` 必须传 `takeWayCode`**，其值取自 `calculate-price` 返回的 `data.takeWayList[].code`。
- **价格单位是「分」**——展示前一律除以 100，转成「元」并保留两位小数。
- **`modification` 的 key 规则**：含 `unselectedKey` 的特调组，组内所有项都必须传入；选中项用 `selectedKey`，未选中项用 `unselectedKey`。
- **`remark` 只在 `orderType=2` 可用**，最长 50 字，且只在外送场景引导用户填写。
- **`beType` 取值**：1 到店自取 / 2 麦乐送 / 5 得来速 / 6 企业团餐。

完整字段与工具说明见 `references/mcp-tools.md`。

## 五、失败处理

| 现象 | 原因 | 应对 |
|---|---|---|
| 401 | Token 无效、过期或缺 `Bearer` 前缀 | 提示用户检查连接器配置中的 `Authorization` 是否为 `Bearer <token>`（注意保留空格） |
| 429 | 超过 600 次/分钟限流 | 降低试算并发，改为串行调用；告知用户稍等 |
| 门店无目标商品 | 该门店未上架 | 用 `query-meals` 列出门店在售替代品，请用户挑选 |
| 用户无可用券 | 券池为空 | 建议 `auto-bind-coupons` 一键领取麦麦省券后重试 |
| 无配送地址 | 未创建地址 | 引导用户在麦当劳 App 中自行添加地址，本 Skill 不代创建 |
| 支付后订单异常 | 状态未同步 | 用 `query-order` 复查，必要时引导用户查看麦当劳 App 订单页 |

## 六、回复风格

- 不使用「已为您切换到某某模式」这类机械声明。

- 沟通卡的正文保持简短，其他解释文字放在卡片之外。
- 不主动提及参赛、评奖等背景信息。
