# 优惠试算策略

本文件说明「麦麦免开口」如何把一堆优惠券变成一张可执行的比价表。

---

## 1. 整体架构：本地穷举 + MCP 核价

```
券池汇总（3 次 MCP 调用）
      │
      ▼
归一化：菜单 + 券 -> 本地数据契约
      │
      ▼
本地穷举 菜篮 × 券组合  ← 不调用 MCP，可试探上千种组合
      │
      ▼
输出 Top-N 候选（含 items[] 与 coupon_ids）
      │
      ▼
calculate-price 逐个核价  ← 只用少量调用
      │
      ▼
择优输出比价表
```

**为什么不让 MCP 参与搜索**：每 Token 每分钟限 600 次请求，若逐方案调用接口，几十个组合就会逼近限流上限；而券的规则一旦归一化，组合搜索完全可以在本地毫秒级完成。MCP 的职责收窄为「把价格算准」。

**关键纪律**：本地估算金额**只用于排序**，绝不能直接展示给用户。任何进入结论的金额都必须来自 `calculate-price` 的返回。

---

## 2. 券的归一化：五种类型

MCP 三个查券工具返回的券需要先归一化成下列结构（金额单位一律为**分**）：

| type | 含义 | 关键字段 |
|---|---|---|
| `item_price` | 单品改价（如「巨无霸立减 7 元」） | `item_codes`、`override_price_fen` |
| `percent` | 单品折扣（如「小食 8 折」） | `item_codes`、`discount_pct`（0.8 = 8 折） |
| `threshold` | 满减（如「满 30 减 5」） | `min_spend_fen`、`discount_fen` |
| `bundle_price` | 组合价（如「麦乐鸡5块 + 可乐(中) 15 元」） | `groups`（每组挑一个）、`price_fen` |
| `free_gift` | 赠品（如「满 20 送派」） | `min_spend_fen`、`gift_codes` |

通用字段：`id`、`title`、`stackable`（是否可与其他券共用）、`channel`（`any` / `pickup` / `delivery`）。

> `channel` 很重要：门店券通常仅到店可用，外送券仅麦乐送可用。搜索前按当前就餐方式过滤，可以避免推荐出无法使用的券。目前门店券一般仅到店可用，外送券仅麦乐送可用。

---

## 3. 券的互斥规则

判定的顺序如下：

1. 两张券中**任意一张 `stackable=false`** → 互斥；
2. 两张都是 `threshold` 或 `free_gift` → 允许共存（门槛不同，可叠加）；
3. 其余情况 → 看两张券**适用的商品是否重叠**，重叠即互斥。

这套规则是本地搜索的基础。真实系统是否允许叠加以 `calculate-price` 的返回为准——被拒的组合直接丢弃即可，不影响其余结果。

---

## 4. 搜索空间控制

组合爆炸是必须防的事，脚本内置四道闸门：

| 常量 | 默认值 | 作用 |
|---|---|---|
| `MAX_STACKED_COUPONS` | 3 | 单方案最多叠几张券 |
| `MAX_CANDIDATES_PER_WANT` | 4 | 每个「想吃的」保留几个候选商品 |
| `MAX_EXTRAS` | 6 | 凑单池大小 |
| `TOP_N_PLANS` | 5 | 最终输出几个方案去核价 |

搜索流程：

1. 按 `wants` 模糊匹配候选商品（名称 > 标签的优先级）；
2. 对候选商品做**笛卡尔积**生成基础菜篮；
3. 为凑满减门槛，额外生成「加购 1 件」「加购 2 件」的变体；
4. 每个菜篮上，枚举不超过 3 张券的所有组合，跳过互斥的；
5. 用 `budget_fen`、`max_calories`、`max_items` 过滤；
6. 按总价升序，取前 `TOP_N_PLANS`。

---

## 5. 核价与择优

把 `plan` 输出的每个方案交给 `calculate-price`：传入该方案的 `items[].code`、`quantity`，以及 `coupon_ids` 对应的 `couponId` / `couponCode`。基准方案（不用券）也要核一次，作为「原价」参照。

把核价结果填入 `verified_total_fen` 后，`verify` 按以下优先级排序：

1. **实付金额最低**（主排序）
2. 实付相同时，**省额更大**者优先
3. 仍相同时，**不使用券**者优先（把券留到下次）

输出必须包含：最优方案的实付金额与券名、相对原价省下的金额与折扣率、其余方案的对照。

**不允许**为了「看起来更省」而推荐分量明显不足、或用户明确没点的商品。若某个更便宜的方案改变了用户想吃的构成，必须标注差异，由用户决定。

---

## 6. 凑单提示

在基准方案与最优方案之间，计算「距离触发下一档更优券还差多少」：

```
当前实付 ¥40.00，距离「满 50 减 8 元」还差 ¥10.00
多买 ¥10.00 可再多省 ¥8.00（实际多花 ¥2.00）
```

只有当「多花的钱 < 多得的好处」或差额极小时才提示；否则明确说明「为凑单而多买并不划算」。

同时检查券池中**即将过期**的券：若本单可用，优先推荐并说明「该券 X 天后过期」。

> 注意分寸：「券快过期了」只是信息，不是催促的理由。如果这张券对应的商品用户本来就不会买，过期并无损失，不应渲染成「你亏了钱」。

## 7. 跨渠道比价

把 `request.json` 的 `dining_mode` 分别设为 `pickup` 与 `delivery` 各跑一次，即可得到「到手价」差异：

| 方案 | dining_mode | 关注差异 |
|---|---|---|
| 到店取餐 | `pickup` | 无配送费，可用门店券 |
| 麦乐送 | `delivery` | 含配送费，券池可能不同 |

输出示例：

```
同一份餐：
  到店自取  实付 ¥45.00
  麦乐送    实付 ¥54.00（含配送费 ¥9.00）

差价 ¥9.00，正好是一单配送费。若能接受走一趟，到店更省；
到店自取走的是取餐柜，同样不用跟店员说话。
```

跨渠道比价会成倍增加核价调用，仅在用户明确关心差价时执行。

## 8. 结果呈现模板

```
商品：巨无霸套餐 ×1 + 麦乐鸡5块 ×1
门店：XX 餐厅（到店自取 · 取餐柜）
原价：¥55.00

方案对照：
  A  满 40 减 10 + 满 20 送香芋派   实付 ¥45.00   ← 推荐
  B  小食 8 折                     实付 ¥52.40
  C  不使用优惠券                  实付 ¥55.00

推荐方案 A，可省 ¥10.00（约 18%），另赠香芋派 ×1。
```

呈现规则：

- 金额一律保留两位小数并带 `¥` 符号
- 推荐项用 `← 推荐` 标注，不使用夸张措辞
- 「省了多少」必须给出绝对值，不用「省很多」这类模糊表达
- 含赠品时单独写出赠品名与价值，不把它混进折扣额
- 券池为空时，直接说明「当前账户与门店没有可用券」，并建议先领麦麦省券

## 9. 命令行速查

```bash
# 本地穷举，产出待核价方案
python scripts/best_coupon_calc.py plan \
  --menu menu.json --coupons coupons.json --request request.json --top 5

# 核价后择优，输出文本比价表
python scripts/best_coupon_calc.py verify --results results.json --format text
```

仓库自带 `scripts/sample_data/` 示例数据，可直接运行体验，无需 MCP Token：

```bash
cd scripts
python best_coupon_calc.py plan \
  --menu sample_data/menu.json \
  --coupons sample_data/coupons.json \
  --request sample_data/request.json
python best_coupon_calc.py verify --results sample_data/results.json --format text
```
